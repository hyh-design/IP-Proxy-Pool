# 大企汇低延迟代理选择优化设计

日期：2026-08-17

## 背景

大企汇捡回系统通过代理池的 `GET /v1/proxies/random` 获取代理。当前线上策略要求代理评分不低于 80，访问 `portal.daqihui.com` 的延迟不超过 1000ms。查询、登录和捡回不得回退到服务器真实出口。

近期观测到代理池总量持续增长，但调用随机选择接口时仍经常返回空列表或仅返回少量代理：

- `portal.daqihui.com` 当前有 2735 个可用代理。
- 评分不低于 80 的可用代理有 2652 个。
- 其中延迟不超过 1000ms 的代理只有 38 个，占 1.43%。
- 连续调用随机选择接口 20 次，每次请求 20 个代理，平均仅返回 1.05 个，7 次返回空列表。
- 最近两天大企汇任务查询错误率从 4.48% 上升到 9.14% 和 11.27%。

根因是当前质量索引同时包含不同健康状态和不同延迟的代理。选择算法先从评分索引随机抽取最多 `count * 25` 条记录，再在内存中过滤可用状态、延迟、新鲜度和连续成功次数。当低延迟代理稀少时，即使池中存在合格代理，也很容易因未抽中而错误返回空列表。

## 目标

1. 始终保持大企汇代理延迟不超过 1000ms 的硬门槛。
2. 不允许自动放宽到 1500ms、2000ms 或其他更高阈值。
3. 不允许回退到服务器真实出口。
4. 当至少存在 20 个符合全部条件的代理时，每次请求稳定返回 20 个。
5. 当符合条件的代理不足 20 个时，返回全部符合条件的代理，不返回不合格代理。
6. 消除因从全部代理中概率抽样造成的错误空列表。
7. 保持代理状态更新、选择和删除过程的一致性。
8. 在 10000 条代理规模下，选择接口 P95 响应时间不超过 100ms。

## 非目标

- 不修改大企汇查询、登录或捡回接口。
- 不调整捡回系统的任务频率和全局限频策略。
- 不修改 1000ms 延迟门槛、最低评分或真实 IP 回退策略。
- 不通过购买代理或增加新的代理来源解决本次选择问题。
- 不在本次改造中重新设计代理评分算法。

## 方案比较

### 方案一：新增可用代理延迟索引

为每个域名新增 Redis 有序集合，仅保存状态为 `available` 且具有有效延迟的代理，排序分数为延迟。选择时直接在指定延迟范围内取候选，再验证评分、新鲜度和连续成功次数。

优点：选择范围准确、性能稳定、不会在大量慢代理中碰运气。缺点：所有代理写入和删除路径都必须同步维护新索引，并需要一次性迁移现有数据。

### 方案二：扩大现有随机抽样

提高当前算法的抽样倍数，必要时重复抽样。

优点：改动较少。缺点：仍然是概率算法，快代理占比继续下降时仍可能错误返回空列表；同时会增加 Redis 命令数量。

### 方案三：每次扫描全部代理

每次调用都读取并过滤当前域名的全部记录。

优点：结果准确。缺点：高频调用下会重复扫描约 10000 条记录，资源消耗不可接受。

采用方案一。

## Redis 数据结构

在现有每域名键集合中新增：

```text
{prefix}:pool:{domain}:available-latency
```

类型为 Redis Sorted Set：

- member：规范化后的代理地址 `IP:端口`
- score：该代理的 `latency_ewma_ms`

该索引只表达“当前状态可用且具有有效延迟”，不把调用方可变的评分、新鲜度和连续成功次数编码进键结构。这样可以保持单一索引，并继续支持 API 提供比全局配置更严格的参数。

加入索引的条件：

- `state == available`
- `latency_ewma_ms` 存在
- 延迟为有限且非负的数值

其他任何状态或无效延迟必须从索引删除。

## 写入一致性

所有能够改变代理状态、延迟或删除代理的路径必须维护新索引：

- `save_record`：在现有 Redis 事务中按记录状态执行 `ZADD` 或 `ZREM`。
- `complete`：扩展完成租约的 Lua 脚本，在保存检测结果时原子更新延迟索引。
- `delete_leased`：扩展删除 Lua 脚本，同时删除延迟索引成员。
- 容量淘汰：删除记录时同步删除延迟索引成员。
- 失败反馈：现有反馈路径经 `save_record` 更新；进入隔离状态时立即移除。
- 候选写入：新候选不进入延迟索引；更新已有记录的来源信息不得破坏已有正确索引。

记录、质量索引、到期索引、租约和延迟索引的更新应保持原子性。不得先返回 API 成功再异步补写延迟索引。

## 选择算法

`random_proxies` 使用以下流程：

1. 将请求的 `max_latency_ms` 与服务端全局上限取更严格值。大企汇线上最终值固定为 1000ms。
2. 使用 `ZCOUNT` 计算延迟索引中 `0..max_latency_ms` 的候选数量。
3. 候选为零时立即返回空列表，不进行慢代理或真实出口降级。
4. 从候选范围内选择一个随机起始偏移量。
5. 使用有界批次从延迟索引读取成员；到达尾部后从开头继续，直到：
   - 已找到请求数量的有效代理；或
   - 已检查该延迟范围内的全部成员。
6. 批量读取代理记录并验证：
   - 状态仍为 `available`
   - 评分满足最终 `min_score`
   - 延迟仍在最终阈值内
   - 最近检测时间满足要求
   - 连续成功次数满足要求
7. 将通过验证的候选随机打乱，返回最多请求数量。
8. 发现索引成员缺少记录、状态不符或延迟越界时，异步或在当前安全写入中从索引移除，完成自愈。

随机起始位置用于避免长期只使用延迟最低的固定一批代理；扫描范围只限于低延迟可用索引，不再从全部 10000 条质量记录中随机碰撞。单次调用最多检查延迟范围内的全部成员，因此只要真实合格代理数量足够，就不会错误少返回。

## 索引迁移与重建

提供一个幂等的索引重建入口：

1. 扫描指定域名的现有代理记录。
2. 将符合索引条件的代理写入临时有序集合。
3. 完成后使用 Redis 原子重命名替换正式索引。
4. 输出扫描数、写入数、忽略数和耗时，但不输出代理认证信息。

重复执行重建必须得到相同结果。可以在旧服务运行期间预构建临时索引以估算耗时和校验数量，但不能直接用这一结果完成切换，因为旧检测器、反馈接口和容量淘汰可能在扫描期间继续修改记录。

正式切换前需要短暂停止代理池的写入组件和 API，基于稳定的记录集合再次快速重建临时索引并原子替换正式索引，然后启动已支持新索引的检测器、采集器和 API。大企汇捡回服务不停止；代理 API 暂时不可用期间只跳过查询，不回退到真实 IP。这样避免扫描结果覆盖并发状态更新，也不会向新 API 暴露半成品索引。

服务启动时检查索引是否存在。生产环境中索引缺失应报告未就绪，不得静默回到旧的概率抽样或真实出口。运维可执行幂等重建后恢复就绪状态。

## 异常处理

- Redis 不可用：随机接口返回 503，捡回系统按现有策略跳过本次查询。
- 没有合格代理：返回空 `items`，不视为服务内部故障。
- 索引缺失：服务未就绪并提供明确错误，禁止旧算法降级。
- 索引存在脏成员：跳过该成员并触发自愈清理。
- 迁移失败：保留原正式索引和旧服务，不执行切换。
- 代理业务请求失败：继续通过现有反馈接口隔离代理，并立即从延迟索引移除。

## 可观测性

新增或补充以下指标：

- 延迟索引总成员数。
- 当前阈值内候选数。
- 通过全部条件的有效候选数。
- 每次请求返回数量。
- 空返回次数及比例。
- 因评分、新鲜度、连续成功次数或索引不一致而跳过的数量。
- 选择接口耗时 P50、P95。
- 索引重建的扫描数、写入数、忽略数和耗时。

代理监控页面应区分“池中可用代理总量”和“满足当前线上选择条件的代理量”，避免用总量掩盖实际可选代理不足。

## 测试设计

### 单元测试

- 可用且有有效延迟的代理加入延迟索引。
- 候选、降级、隔离代理不进入索引。
- 状态从可用变为隔离时从索引删除。
- 延迟更新后有序集合分数同步更新。
- 删除、容量淘汰和租约完成路径同步维护索引。
- 1000ms 边界值可以返回，超过 1000ms 不返回。
- 评分、新鲜度和连续成功次数过滤正确。
- 索引脏成员被跳过并清理。

### 回归测试

构造 9962 个慢代理和 38 个满足全部条件的快代理：

- 连续执行多次 `count=20` 请求，每次返回 20 个。
- 返回结果全部来自 38 个快代理。
- 多次调用能够覆盖不同快代理，不固定使用同一小组。
- 将合格代理减少为 12 个后，每次返回全部 12 个。
- 将合格代理减少为 0 个后返回空列表，不出现阈值降级。

### Redis 集成测试

- 事务写入失败时记录和所有索引保持原状态。
- 租约完成 Lua 脚本原子更新新索引。
- 并发检测、反馈和选择不会返回已隔离代理。
- 索引重建过程中正式索引保持可读。
- 重建重复执行结果一致。

### 性能测试

在 10000 条记录和不少于 38 条低延迟代理的数据集下：

- 选择接口 P95 不超过 100ms。
- Redis 命令数量有明确上限，不随全部代理数量线性增长。
- 高频并发读取不会阻塞检测器更新。

## 部署步骤

1. 构建并测试新的代理池镜像。
2. 备份当前 Redis 数据或确认可恢复快照。
3. 在旧服务继续运行时预构建临时索引，估算迁移耗时并初步校验数量；该索引不用于正式切换。
4. 短暂停止代理池 API、检测器和采集器，保持大企汇捡回服务运行。
5. 基于稳定记录集合重新构建临时索引，校验成员数与全量计算结果一致，再原子替换正式索引。
6. 启动新检测器和采集器，使所有后续写入维护新索引。
7. 启动新 API 服务，切换到新选择算法；短暂不可用期间继续遵守“不走真实 IP”的行为。
8. 连续调用选择接口 20 次，核对返回数量、延迟上限和地址多样性。
9. 观察至少 30 分钟的大企汇查询错误率、代理空返回率和选择耗时。

## 回滚

- 回滚 API、检测器和采集器到原镜像。
- 新增延迟索引不影响旧版本，可暂时保留以便排查。
- 如需删除新索引，只删除新增键，不修改原记录、质量、到期和租约数据。
- 回滚不得修改大企汇任务频率、认证信息或真实 IP 回退策略。

## 验收标准

- 线上继续执行 `max_latency_ms=1000`，没有更高延迟或真实出口回退。
- 全量计算存在至少 20 个真实合格代理时，连续 100 次请求均返回 20 个。
- 全量计算不足 20 个时，接口返回数量与真实合格数量一致。
- 连续 100 次请求中没有由抽样遗漏造成的空列表。
- 所有返回代理的状态、评分、延迟、新鲜度和连续成功次数均满足要求。
- 选择接口 P95 不超过 100ms。
- 部署后 30 分钟内代理空返回率显著下降，且大企汇查询错误率不高于部署前同长度观察窗口。
- 代理池各容器、Redis 和大企汇捡回服务保持健康。
