# 优质代理优先复测与大企汇自动恢复设计

## 背景与根因

线上代理池保存约 10,000 条记录，但大企汇只允许使用同时满足以下条件的代理：评分达到既定门槛、延迟不超过 1000ms、连续成功次数达到门槛，并且最近 600 秒内完成过检测。

现有 Checker 只按通用 `due` 队列领取任务。大量候选或低质量代理使用较短复测周期，导致已经验证过的低延迟代理长期排在通用队列后面。2026-08-17 现场数据中，延迟不超过 1000ms 的 39 条记录全部处于到期状态，最近检测时间最短也已超过 600 秒，因此 API 在不降低质量门槛的情况下返回空列表。

大企汇调度器按 0.01–0.1 秒频率运行。代理暂时为空时，当前客户端会立即失败并进入下一轮，形成高频错误、钉钉通知和统计写入；代理恢复后，进程内缓存及失败状态也不能可靠地自动恢复。

## 目标

- 保持评分、1000ms 延迟上限、600 秒新鲜度和连续成功次数门槛不变。
- Checker 优先复测满足低延迟可用条件的代理，同时继续检测普通候选，避免饿死通用队列。
- 代理暂时为空时，大企汇不直连、不泄露真实 IP、不发送钉钉错误通知，也不计入大企汇平台查询错误。
- 代理重新出现后，大企汇无需重启即可自动恢复。
- 所有 Redis 索引更新和领取操作保持原子性，支持已有数据重建。

## 方案

### 代理池：优质代理复测队列

在每个域名现有的 `due`、`leased` 和 `available-latency` 索引旁新增 `priority-due` ZSET：

- 成员：状态为 `available`，且延迟不高于当前 `selection.max_latency_ms` 的代理。
- 分值：与通用 `due` 相同，使用 `next_check_at` 时间戳。
- `save_record`、候选更新、检测完成、租约释放和反馈更新必须在同一 Redis 事务或 Lua 脚本中同步维护该索引。
- 延迟索引重建命令同时重建 `priority-due`，以便升级后立即覆盖现有数据。

Checker 每轮领取任务时：

1. 先从 `priority-due` 领取已经到期的成员，并同时从通用 `due` 删除、写入租约。
2. 使用本轮剩余额度从通用 `due` 领取其他成员。
3. 一轮最多仍为现有 `batch_size`，因此不会提高 Checker 的总并发或请求量。
4. 优质代理数量通常远小于批次容量，普通候选仍能持续获得检测机会。

该方式只改变检测顺序，不降低筛选门槛，也不扩大外部请求并发。

### 大企汇：共享退避与错误分类

`ProxyPoolClient` 在代理 API 返回空列表时进入全局 5 秒冷却：

- 所有任务共享同一个客户端、锁和冷却截止时间。
- 冷却期间不重复请求代理池；到期后只允许一个调用刷新候选，其他调用复用结果。
- 刷新仍为空时重新进入冷却；一旦返回候选，立即清除不可用状态并恢复正常轮询。
- 不允许直连回退。

新增独立的“代理暂不可用”运行结果分类：

- 不加入 `query_errors` 或 `reclaim_errors`，因此不触发钉钉错误通知。
- 不计入大企汇平台查询错误，也不伪装成正常空查询。
- 在分钟及每日统计中独立累计 `proxy_unavailable_count`；精简日报仅在该值大于 0 时追加一行。

连接超时、代理握手失败等明确的代理链路错误沿用同一通知抑制规则；大企汇接口返回异常仍按原有查询错误处理。

## 数据一致性与升级

- 为 `priority-due` 使用独立键名和版本就绪标记。
- API 和 Checker 启动就绪检查必须确认优先索引已完成重建，避免半升级状态提供服务。
- 部署前备份 Redis RDB、两个项目源码与大企汇 SQLite 数据库。
- 先停止大企汇，再升级并重建代理索引；代理 API/Checker 就绪后启动大企汇。
- SQLite 新统计字段通过幂等迁移添加，旧数据默认值为 0。
- 回滚时恢复旧镜像与源码；新增 Redis 键和 SQLite 列可安全保留。

## 测试

### 代理池

- 优质记录保存、降级、删除和延迟变化时，`priority-due` 成员关系正确。
- 优先领取同时更新两个 due 索引及租约，重复领取不会发生。
- 优质数量少于批次时，剩余额度来自通用队列。
- 普通队列持续获得额度，不因优质队列长期饿死。
- 重建命令生成与全量记录一致的 `available-latency` 和 `priority-due`。
- 并发领取、租约过期回收和旧 Worker 完成写回保持一致。

### 大企汇

- 空候选触发一次刷新和全局冷却，不产生高频代理池请求。
- 多任务并发时只有一个刷新者，其他调用复用状态。
- 冷却后候选恢复，无需重启即可继续查询。
- 代理暂不可用不发送钉钉、不计查询错误，并单独进入统计。
- 平台 4xx/5xx、非 JSON 和业务错误仍保持原有错误分类。

## 线上验收

- 代理池 `ready`，优先索引标记有效。
- 连续 20 分钟内，延迟 ≤1000ms 且满足完整门槛的可选代理不出现周期性归零。
- 大企汇八个任务持续产生分钟统计，没有代理空窗导致的查询错误风暴。
- 通过线上真实 HTTP 登录与只查询检查，确认不使用 Playwright，也不发生直连回退。
- 对比部署前后 Checker 总并发与请求量，确认没有提高既定上限。

## 非目标

- 不降低代理评分、延迟、新鲜度或连续成功门槛。
- 不允许登录、查询或捡回接口绕过代理。
- 不调整大企汇正常时间段的查询频率。
- 不改变捡回成功、被抢和平台接口错误的现有通知规则。
